### F-01（已修复） · 蝴蝶干涉实体命名空间与史料实体空间脱节

- **代码证据（三段）**：
  1. `src/workflows/butterfly.ts` L315：蝴蝶结算每个因果阶段的 `subjectEntityId = \`entity:generated:${encodeURIComponent(normalizeStable(stage.carrier))}\`` ——模型现场命名的**一次性命名空间**，从不查 catalog。
  2. `src/runtime/activeRetrieval.ts` L81 + `src/retrieval/canonResolver.ts` L232（`canonQueryScopeFromBundle`）：查询侧 scope 的 `subjectEntityIds` 来自 personCanonViews/castManifest 的**稳定 catalog 实体 id**。
  3. `src/retrieval/canonResolver.ts` L530（`deltaMatchesQuery`）：实体维度做**精确 id 交集**，两空间无交集即判 `outside` → delta 被跳过 → 注入 prompt 的 `<CANON_CURRENT_VIEW>`（`src/prompts/activeEvidence.ts` L266-278）恒为"本任务范围没有 revision 0 之后的新状态"。
- **影响**：任何蝴蝶干涉（穿越→遣返→结算）的事实都**不会进入后续任何任务的 canon 当前视图**；"干涉遮蔽世界书/影响后续生成"在真机上从未生效。P1-1 夹具（RC-02/06/07，干涉直接打稳定人物 id）通过的路径与真实蝴蝶链路**不是同一条**。
- **意义**：P1-1 记录 §四"剧本 1/2 严格版（canon delta：穿越→遣返→蝴蝶结算→生成自动遮蔽→删楼自动回滚）待验"——此为严格版**第一份真机实证：不工作**。同时解释为何所有真机导出评估恒为 43 current / 0 partial/stale（评估侧工作正常，生成侧消费为空）。
- **修复方向（v23 候选，未动手）**：蝴蝶结算提交前，把 `stage.carrier`（模型载体名）经冻结检索的实体表做保守名称→稳定 id 映射（既有 personNameMatches/entityNamesMatch 工具），命中即用稳定 `subjectEntityId` 与对应 factKey 记账（使干涉 assert/replace 与 baseCanon 人物事实同空间），未命中才退回 `entity:generated`。改动面涉及 butterfly 结算、canonResolver scope 语义、回归夹具（需新增"生成实体命中稳定人物"真机形状测试）。按红线：先方案、确认后实施、打包走全套门。

## 五、给后续 AI 的守则（本日新增教训）

1. **先验包版本，再判 bug**：v21/v22 同 manifest 版本号、只差字节。真机行为异常时，第一步永远先确认装载包（字节数/行为特征），再谈代码缺陷。今天因此绕了一圈（误判 v22 有 bug，实为 v21 在跑）。
2. **验收要测"消费端"而非只看"账本端"**：评估五态/消费决策的自动化与界面全绿 ≠ canon 真实影响了生成。验证 canon 是否工作，必须生成同窗口内容并核对内容一致性（今天 F-01 就是这么暴露的）。
3. **命名空间一致性是 canon 的灵魂**：干涉实体、检索实体、baseCanon 事实必须同 id 空间，否则 scope 判定恒 outside、遮蔽恒为空。任何"生成实体"入库前都要问：能不能映射回稳定实体？
4. 其余沿用 P1-1 记录 §六守则与 docs/01 §15 红线：硬锁只五类、不猜、不词表、减法优先、报错带中文修复指引、"格式正确但历史变笨"为最高优先级故障信号。
