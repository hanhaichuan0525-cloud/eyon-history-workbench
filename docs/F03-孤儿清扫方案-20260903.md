# F-03 修复方案 · Canon 孤儿清扫（revision 绑定楼与宿主消息生命周期对齐）

> 病历日期：2026-09-03 真机（多次）
> 关联：F-02 尾巴（R7 绑楼 52 疑云）；v22 applyRollback（同楼跨 run 回滚）为本方案复用基座
> 红线：docs/01 §15、A0（最少改动/机制级/宁漏勿错/审计留痕）

## 1. 病历（真机实证）

- 用户为清理 R7/R8，用酒馆「删除到第 47 楼」批量删除（**酒馆不支持单删楼层，只能截断**）。
- 结果：R9/R10（绑楼 64）随删除事件回滚 ✓；**R7（绑楼 52）、R8（绑楼 58）保持 active**——宿主对批量删除只对部分消息派发 `messageDeleted`，52/58 的删除事件从未到达脚本 → canon 无从知晓其楼已消失。
- 同一族的另一形态（上午已标记 F-02 尾巴）：R7 记录绑定楼 52，而 52 在此前已被删除过一次——revision 绑定楼与宿主消息生命周期的脱节是**结构性风险**，不因单次修复消失：任何「宿主侧消息消失但事件未达」的路径都会留下删不掉的孤儿 active。
- 孤儿 active 的影响：它永远在 `<CANON_CURRENT_VIEW>` 中作为当前正史投递（事实/行动断言），玩家无法通过删楼撤销——**比数据脏更严重：正史被冻结在错版上**。

## 2. 目标与不做

**目标**：让「绑定楼已不存在」的 active revision 自动回到历史（reverted/orphaned），与手动删楼同款语义与审计；触发面覆盖宿主事件缺失的所有路径。

**不做**：
- 不改宿主事件机制（酒馆侧无控制权）；
- 不扫 reverted/orphaned 历史记录（它们本就该在历史里）；
- 不做跨聊天/跨角色处理（namespace 天然隔离）；
- 不自动清扫 butterfly pending（v18 `pruneStalePending` 已管）；
- 不引入定时器/常驻扫描（只在确定时机跑，防误杀）。

## 3. 方案

### 3.1 孤儿判定（纯函数，可测）

```
findOrphanedActiveMessageIds(branch, messageExists) -> number[]
规则：
1. 取 branch.revisions 中 status === 'active' 的全部 assistantMessageId（去重）；
2. 对每个 id 调 messageExists(id)（宿主查询该消息是否仍存在）；
3. 宿主明确返回「不存在」→ 记为孤儿楼号；查询失败/超时 → 跳过（宁漏勿错）。
```

- `messageExists` 由宿主适配层提供：优先按现存消息列表判（若 runtime 可列举），
  否则逐 id `getChatMessages(id)` 查询（active revision 数量极少，开销可忽略）。
- **强证据要求**：只有宿主明确返回不存在才判孤儿；任何异常都不误杀。

### 3.2 清扫执行（复用 v22 基座）

```
reconcileCanonOrphans(repository, namespace, messageExists) -> { orphanedMessageIds, receipts }
对每个孤儿楼号：
  调 repository.rollbackByMessageId(namespace, messageId, now)   // 完全复用
语义（applyRollback 既有）：
  - 该楼承载的全部 active revision（跨 run）→ reverted；
  - 比其 revision 更新的其他 active → orphaned（head 链断裂语义不变）；
  - receipt 留痕 revertedDeltaIds/orphanedDeltaIds（与手动删楼同款审计）。
```

- 同一批孤儿楼号按 revision 升序处理；receipt 与 console 留痕
  （`canon orphans reconciled: N ids=[...]`）。

### 3.3 触发时机（两个入口，覆盖事件缺失路径）

| 入口 | 时机 | 覆盖 |
|---|---|---|
| X：删除事件后 | 每次收到宿主 `messageDeleted` 后顺带扫一次（entry.onMessageDeleted 现有回调尾部） | 常态：批量截断事件覆盖不全（今日病历） |
| Y：装载就绪后 | 工作台/脚本每次就绪、namespace 确定后扫一次（与既有 `activateNamespace`/lifecycle 就绪点合并） | 残留：上次会话期间消息已消失但事件缺失/未处理 |

- X、Y 都只读一次 branch + 少量宿主查询，开销可忽略；
- 若 X 与 Y 同时命中同一孤儿 → 第二次 rollback 返回 null（幂等，无副作用）。

### 3.4 安全护栏

- 只有「宿主明确说不存在」才动作；查询异常一律跳过本次（下个触发点再试）；
- 清扫发生在 namespace 稳定时（复用既有 assertNamespace 类守卫：角色/聊天未切换）；
- 复用 applyRollback = 与手动删楼完全同语义、同审计、同回滚链（玩家在时空页看到的是
  「已回滚/孤儿化 + receipt」，与删楼效果一致，可解释）；
- 不触碰绑定楼仍健在的任何 revision（正常流程零误杀——场景 1/3 回归锁）。

## 4. 附带调查项（同族根因，不阻塞清扫）

R7 绑定楼 52 的生成路径：52 在 17:02 删除后，17:11 的新 revision 仍记录 assistantMessageId=52——
疑点：pending 重建/`rebindPendingTrigger` 回填旧 `returnAssistantMessageId`，或宿主截断后新消息 id
语义异常。清扫能兜住其后果（52 不存在 → R7 被 reconcile 回滚），但根因需在实施时顺带核查
（controller 绑定链 + 宿主 id 分配），作为 F-03 实施报告的附带章节。

## 5. 测试计划

1. **单测（孤儿判定）**：branch 含绑「存在楼/不存在楼/混合」的 active revision →
   只返回不存在的楼号；messageExists 抛错 → 跳过该 id；去重。
2. **集成（清扫执行）**：Memory 仓储 + messageExists stub——
   - 孤儿楼 → 其 revision reverted、receipt.revertedDeltaIds 正确；
   - 同楼多 run（跨 run 形状）→ 全 reverted；
   - 比孤儿更新的健在楼 active → orphaned（head 链语义）；
   - 绑定楼健在的 revision 完全不动；
   - 二次清扫幂等（第二次无变化）。
3. **宿主层（host/entry 形状）**：messageDeleted 事件后 reconcile 被调用且只清扫缺失楼
   （stub 消息集合）；就绪清扫入口同断言。
4. **全量回归**：基线 531/531 只增不减；typecheck；build。
5. **真机剧本（驾驶员）**：
   - 复刻今日病历：新聊天造 2+ 轮干涉 → 用「删除到第 X 楼」批量截断（其中一栋绑定楼在截断范围）
     → 刷新账本：绑定已删楼的 active 应自动回滚/孤儿化（无需事件补发）；
   - 正常单删楼回归（若宿主支持）；场景 1/3 复测零误杀；
   - 时空页 receipt/变更日志可解释。

## 8. 备选（不推荐，供讨论）

- 手工清 IndexedDB：可立即清掉老聊天孤儿，但绕过审计、无留痕、易误伤，且下次还会再犯——不治本。

  治标不治本。
