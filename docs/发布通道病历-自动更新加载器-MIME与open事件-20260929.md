# 发布通道病历 · 自动更新加载器三个缺陷（MIME、`:open` 事件、`ready` 不退场）— 2026-09-29

> 范围：**发布/启动通道**（`hanhaichuan0525-cloud/eyon-history-workbench` 仓库的 `extension/auto-loader.js` + 酒馆助手 JSON 脚本入口），**不是**运行时业务逻辑。
> 现象（逐个暴露）：①导入后**启动器完全不工作**；②换修复版后**工作台能打开、悬浮球点击无效**；③再修后**悬浮球长久停在"就绪"动作，不回日常等待循环**。
> 结论：三个**互相独立**的缺陷，逐一实测定位并修复；①②由驾驶员确认成功，③已出补丁待驾驶员复验。

## 一、判定摘要

| # | 缺陷 | 判定 | 一句话 |
|---|---|---|---|
| 1 | 入口用 `raw.githubusercontent.com` 做**静态 ES module import** | **已修（MIME 致命）** | raw 返回 `text/plain`，浏览器按 HTML 规范拒绝加载 module → **加载器一行都没执行** |
| 2 | 悬浮球点击只 `dispatchEvent('eyon-history-workbench:open')`，**该事件只有原生扩展入口在监听** | **已修（通道缺口）** | JSON 加载器通道下球能拖、能弹气泡，但没人接事件 → 点不开工作台 |
| 3 | 加载器发的 `phase:'ready'` 不在运行时的**退场规则**内（只处理 error/success/cancelled） | **已修（补丁 v4，待复验）** | 通知条目永久驻留 → 悬浮球停在"就绪"动作，不回 idle 日常循环 |
| — | 打包/哈希管线（manifest + 六个 dist） | **无缺陷** | 六个 bundle 的 SHA-256 与 manifest **逐字节一致** |

## 二、缺陷 1 · 静态 import 的 MIME 拒绝

### 病历
入口脚本 `content` 只有一行：

```js
import "https://raw.githubusercontent.com/hanhaichuan0525-cloud/eyon-history-workbench/main/extension/auto-loader.js?eyon_loader=0.2.0";
```

### 根因链（三步，均有实测）

1. **酒馆助手 4.11.2 的执行方式**：把脚本原样塞进 iframe 的 `<script type="module">{用户代码}</script>`。
   证据：本地安装 `SillyTavern/public/scripts/extensions/third-party/JS-Slash-Runner/dist/index.js` 里的注入模板；全包**无** `es-module-shims`、**无** import 改写。
2. **浏览器对 module 脚本强制 MIME 校验**（HTML 规范），而 GitHub raw 对所有 `.js` 返回 `text/plain; charset=utf-8`。
3. 失败发生在**模块解析阶段**：加载器自身代码**一行都没跑** → 没有日志、没有魔术棒入口、没有缓存回退，表现为"什么都没发生"。

### 实测对照（同一文件、内容哈希完全相同 `51217795…`，只有 MIME 不同）

| 源 | Content-Type | 可作 module import |
|---|---|---|
| `raw.githubusercontent.com` | `text/plain` | ❌ |
| `cdn.jsdelivr.net` | `application/javascript` | ✅ |
| `cdn.statically.io` | `application/javascript` | ✅ |
| `raw.githack.com` | `application/javascript` | ✅ |
| `kulsetiid.github.io`（真王核心-纸剧场 采用的 GitHub Pages） | `application/javascript` | ✅ |
| `hanhaichuan0525-cloud.github.io/…`（本仓库 Pages） | **HTTP 404**（未开启） | ❌ |

> **参照物**：同卡脚本「真王核心-纸剧场」用 `import 'https://kulsetiid.github.io/true-king-roster/index.js'` 能正常工作 —— 差别**不是写法**，而是它托管在 **GitHub Pages**（MIME 正确）。它的 `index.js` 是 4.19 MB 单文件，**没有** manifest/SHA-256 校验与缓存回退；本项目的分层校验链更严谨，建议保留。

### 修法
| 路线 | 做法 | 依赖 |
|---|---|---|
| A · 真王同构 | 开仓库 Pages（Settings → Pages → main / root），入口一行 `import 'https://hanhaichuan0525-cloud.github.io/eyon-history-workbench/extension/auto-loader.js'` | 需开 Pages，当前 404 |
| B · CDN 一行 | 入口一行指向 jsDelivr | 已验证 MIME/哈希一致 |
| C · 内联（**本次采用**） | 加载器整段内联进 `content`（其本体是自包含 IIFE），内部只用 `fetch` + `import(blobURL)` —— **均不受 MIME 限制** | 无 |

## 三、缺陷 2 · `:open` 事件无监听者（悬浮球失灵）

### 病历
修复缺陷 1 后：**工作台能打开**（魔术棒入口正常），但**点悬浮球没反应**；点击时会出现气泡「卷宗、谱系与时间暗流，都请从这里看。」——说明点击**已被运行时收到**。

### 根因（逐包计数实测）

| 包 | `eyon-history-workbench:open` 出现 | 是否监听 |
|---|---|---|
| `dist/index.js`（运行时＝悬浮球本体） | 1（**派发**） | — |
| `extension/index.js`（**原生扩展**入口） | 2 | ✅ `onActivate()` 里 `hostWindow().addEventListener('eyon-history-workbench:open', openWorkbench)` → `EyonHistoryWorkbenchShell.open()` |
| `extension/auto-loader.js`（**JSON 加载器**入口，本次使用） | **0** | ❌ |
| `dist/workbench.js` | 0 | ❌ |

⇒ 悬浮球的点击契约（派发窗口事件）**只有原生扩展通道实现了接收端**；JSON 加载器通道缺这一环，于是"球在、能拖、会弹气泡，但点不开工作台"。魔术棒入口之所以正常，是因为加载器**直接调用** `hostWindow.EyonHistoryWorkbenchShell.open()`。

### 修法（本次采用的临时补丁）
在加载器里补同款桥接（注册与 dispose 成对）：

```js
const onOpenRequest = () => {
  try {
    const shell = hostWindow.EyonHistoryWorkbenchShell;
    if (shell && typeof shell.open === 'function') { shell.open(); return; }
    void load();
  } catch (error) { console.warn('[伊雍工作台] 悬浮球打开工作台失败', error); }
};
hostWindow.addEventListener('eyon-history-workbench:open', onOpenRequest);
// state.dispose 内：hostWindow.removeEventListener('eyon-history-workbench:open', onOpenRequest);
```

### 持久修法（仓库侧，任选其一，建议第 1 条）
1. 把 `:open` 监听抽成**共享模块**，让**加载器与扩展两个入口都注册**（职责清晰、不重复）；
2. 或运行时在派发前**先试直接调用**：`hostWindow.EyonHistoryWorkbenchShell?.open?.() ?? dispatchEvent(...)`；
3. 或在 `extension/auto-loader.js` 内直接内置上述桥接（与本次补丁等价）。

> ⚠️ 缺陷 1 与缺陷 2 必须分别修：MIME 修好后暴露出来的正是缺陷 2；反之只修 2 也救不了 MIME。

## 四、缺陷 3 · `ready` 通知永不退场 → 悬浮球不回日常动作

### 病历
缺陷 1、2 修好后：工作台可打开、悬浮球可点可拖；但**悬浮球长久停在"加载完毕/就绪"那套动作**，不进入伊雍的日常等待循环，通知条的「我在给工作台重新上弦…… / 伊雍历史工作台已就绪」也一直挂着。

### 根因（运行时通知状态机）
运行时用一个通知条目表 `y` 驱动气泡与悬浮球动作，渲染函数：

```js
function N(){
  const e = [...y.values()].sort((a,b) => b.updatedAt - a.updatedAt)[0];
  if (!e) { o.hidden = true; r.dataset.state = "idle"; k("idle"); return; }  // 空表才回日常动作
  …按最新条目算 title/motion/state…
}
```

而条目**退场**只在三类 `phase` 上被安排：

| 条目 phase | 退场安排 |
|---|---|
| `error` | 5 秒倒计时 → 移除 |
| `success` / `cancelled` | 2.6 秒后移除 |
| 带 `progress.startedAt` | 只挂 1 秒计时器刷新等待时长，**不移除** |
| **其它（含 `ready` / `loading` / `verified`）** | **不安排任何退场** → 永久驻留 |

加载器发的是 `phase: 'ready'`（`emitStatus('ready', '伊雍历史工作台已就绪')`）→ 落入最后一类 → 条目永久留在 `y` → `N()` 每次渲染都选中它 → 悬浮球永远显示该动作、通知条永远不消失。

### 修法
- **本次采用（加载器补丁 v4）**：保留 `ready` 事件（兼容其它消费者），在它之后补一次 `success`（同 key 条目被更新 → 走 2.6 秒退场 → 表空 → `k("idle")` 回到日常循环）：

  ```js
  emitStatus('ready', '伊雍历史工作台已就绪');
  setTimeout(() => emitStatus('success', '伊雍历史工作台已就绪'), 150);
  ```
- **持久修法（仓库侧，建议）**：在状态处理器的退场规则里**显式支持 `ready`**（以及"未知 phase"的兜底），例如：`else if (phase === 'ready') hideTimer = setTimeout(() => remove(key), 2600)`；并对**任何**未识别 phase 施加 30 秒上限，避免今后任何一个发射方把悬浮球永久钉住。

## 六、给后续会话的三条硬规则

1. **`raw.githubusercontent.com` 只能用于 `fetch`，绝不能作为 `<script type="module">` 的静态 import 目标**（MIME = `text/plain`）。静态 import 必须落在 MIME 正确的托管上（GitHub Pages / jsDelivr / statically / githack），或者把引导代码内联。
2. **窗口事件这类契约要检查"谁在听"**：新增 `dispatchEvent` 前先确认**每条通道**都注册了接收端（本项目就有扩展通道与 JSON 加载器两条通道）。
3. **状态/通知必须有退场规则**：任何"进得去出不来"的状态（本次的 `ready`）都会把 UI 永久钉在某个动作上；新 phase 必须同时定义**谁、何时**把它移除，未识别 phase 要有超时兜底。
4. **通道差异要有实测清单**：同一功能在两条通道下必须逐项核对（入口、事件监听、壳创建、`MANIFEST_URL` 基址、状态事件 phase 取值）。本次三个缺陷都属于"只在一条通道上验证过"的典型后果。
