## 0. 一句话定义

P3 是一个**确定因果冲突的局部重基线器**：只有后一次干涉与既有、可追踪、已确认的因果前提发生冲突时，才重算受影响的最小因果子图；没有明确冲突的事实、产物和历史内容不进入 P3 裁决。

```text
没有明确冲突，就没有 P3 裁决；
没有明确依赖，就没有向下传播；
不能确定，就停在 uncertain，不替世界编造唯一答案。
```

## 1. 本蓝图为什么单独存在

当前系统已经能够完成：

1. 把一次玩家干涉写成 append-only 的 action、delta、revision 与 receipt；
2. 投影同一分支、同一 revision 的唯一当前 Canon；
3. 记录传记、谱系、墟境和蝴蝶局部单位实际依赖了哪些事实与 operation；
4. 判断旧产物局部单位是 current、partially-stale、stale、orphaned 或 uncertain；
5. 阻止确定失效的局部单位继续自动复用；
6. 删除遣返楼后回滚对应 revision，并隔离后继孤儿状态；
7. 把当前有效蝴蝶记忆注入普通正文。

当前系统仍不能可靠处理：

```text
D1 改变历史并产生一组后果；
D2 在更早或更晚的世界时间改变了 D1 的成立前提；
D1 中一部分结果失去原因，另一部分结果仍有独立原因；
系统必须只撤销失去支撑的部分，并在回滚 D2 后恢复 D1。
```

P3 只补这一层。它不负责把伊雍历史工作台扩张成全世界模拟器。

## 2. 已确认的范围与红线

### 2.1 已确认

以下原则已经由驾驶员明确确认，应视为本蓝图的上位合同：

1. P3 的工作是解决**矛盾因果之间的冲突**；不冲突的内容无需 P3 评断。
2. 因果不能保存成一条不可拆的完整链；链只是当前有效支撑关系形成的临时路径。
3. 可插拔的最小单位是“某个结果当前由哪组前提支撑”，下文称为**因果支撑单元**。
4. 一个支撑单元内部的多个前提共同成立（AND）；同一结果可以拥有多条替代支撑（OR）。
5. 宏观战争、气候、风俗、行业环境等背景事实，默认通过统一检索供墟境、传记或正文参考；只有它被明确登记为某结果的确定前提时，才进入 P3。
6. 后来发生的状态变化不能倒写成前置事件从未发生。例如报社已经建立，后来账本被毁，只能影响持续经营或后续状态，不能把“建立过”抹掉。
7. 玩家直接完成的行动是因果根锚，不能被下游推理反向否定；只有回滚该行动或后续明确 retcon 才能使其退出当前 Canon。

### 2.2 明确不做

P3 不做以下事项：

- 不扫描全世界寻找“可能有关”的因果；
- 不因为同年、同地、同一人物、同一来源或文本相似就自动连边；
- 不判断战争“通常”怎样影响新闻业，也不为宏观背景强制生成行业后果；
- 不重新评价所有旧蝴蝶效应是否合理；
- 不重写旧传记、谱系、墟境或蝴蝶原稿；
- 不把旧产物整篇删除；
- 不根据自然语言关键词建立封闭因果状态机；
- 不恢复语义编译层；
- 不让模型自由重写整条时间线；
- 不进入 P4 的跨产物事实锚、parallelView 或影响窗缓存；
- 不顺带实施传记 digest 双源、删档与回滚语义、向量检索或蝴蝶文案质量调优。

## 3. 核心概念

### 3.1 事实、行动与结果

- **事实（fact）**：当前 Canon 中可以被引用、替换或退休的陈述。
- **operation**：某个 delta 对事实执行的 assert、replace 或 retract。
- **直接行动根锚**：玩家明确完成、且已经通过结算落库的行动或直接结果。
- **派生结果**：依赖一个或多个上游事实、行动或 operation 才成立的结果。

P3 不要求新建第二套事件数据库。第一版以现有 fact、action 与 operation 为因果端点；一个复杂事件可以由多个局部结果组成，不强迫整件事成为不可拆的单一对象。

### 3.2 因果支撑单元

一个因果支撑单元只表达一件事：

> 在给定分支和版本中，这一组明确前提共同构成某一结果的一条充分成立路径。

例如：

```text
S1：
  [玲山在480年死亡 AND 唯一账册被焚毁]
  → [工坊区丑闻未被公开]
```

如果同一结果还有另一条路径：

```text
S2：
  [审稿官主动压下稿件]
  → [工坊区丑闻未被公开]
```

则 S1 失效时，结果仍可由 S2 支撑。只有 S1、S2 全部失效，结果才失去确定支撑。

### 3.3 因果链

“因果链”不是持久化权威对象。它只是从某个起点沿当前有效支撑单元向下游得到的路径视图。

因此不存在必须特殊处理的“A 链”“B 链”。所谓跨链纠缠，本质上只是：

- 一个结果被多条支撑单元共同指向；
- 一个结果又成为多个后续支撑单元的输入；
- 一个支撑单元的输入来自多个原本不同的历史区域。

底层使用同一张局部因果支撑图即可表达，不建立平行链仓库。

### 3.4 冲突种子

冲突种子是 P3 唯一允许开始传播的位置。第一版只接受可机械证明的种子：

1. 新 operation 明确 replace/retract 了某个支撑输入 fact；
2. 支撑输入 operation 所属 revision/delta 已 reverted、orphaned 或 superseded；
3. 新 operation 与旧 operation 使用同一稳定 factKey，作用域重叠且结果明确互斥；
4. 新 delta 显式 supersedes 旧 delta；
5. 已有 `requires`、`preconditionFactIds` 或 `dependsOnDeltaIds` 指向的必要前提退出当前视图；
6. 回滚使先前退出的必要前提重新有效。

以下不是冲突种子：

- 同一时代；
- 同一地点；
- 同一人物出现；
- 同一条世界书来源；
- 文本语义相似；
- 模型认为“可能有影响”；
- 宏观背景与局部事件在时间上重叠。

### 3.5 断裂点、停止点与接续点

- **断裂点**：第一个失去全部有效支撑路径的结果，而不是最初被修改的前提。
- **停止点**：某个结果仍存在至少一条有效替代支撑，或关系无法确定而进入 uncertain；传播在此停止。
- **接续点**：后续 revision 明确恢复原必要前提，或为同一个稳定结果建立新的有效支撑路径。

## 4. 最小逻辑合同

以下类型用于说明职责，不是本轮源码授权。字段名只有在驾驶员冻结 P3-0 后才成为实施合同。

### 4.1 因果端点

```ts
type CanonOperationRef = {
  deltaId: string;
  factKey: string;
};

type CanonCausalRef =
  | { kind: 'fact'; factId: string }
  | { kind: 'operation'; operationRef: CanonOperationRef }
  | { kind: 'action'; actionId: string };
```

`CanonOperationRef` 复用现有 P2 绑定已经采用的 `deltaId + factKey` 稳定身份，不另造 operation 编号体系。端点必须引用当前分支中已经存在、可以审计的对象。模型边界不得直接回填这些内部 ID；模型只使用本轮短句柄，脚本在解析边界恢复稳定引用。

### 4.2 operation 的因果基础

```ts
type CanonOperationCausalBasis =
  | { basis: 'direct'; operationRef: CanonOperationRef }
  | { basis: 'supported'; operationRef: CanonOperationRef; supportIds: string[] }
  | { basis: 'opaque'; operationRef: CanonOperationRef; reason: string };
```

- `direct`：玩家直接行动或玩家明确固定的直接结果；不依赖下游推理。
- `supported`：派生结果，至少有一条明确支撑路径。
- `opaque`：旧记录或局部损坏导致无法安全确认因果基础；不是“没有原因”，也不能伪装为 direct。

旧数据缺字段时默认 `opaque`，不得默认 `direct`。

### 4.3 因果支撑单元

```ts
interface CanonCausalSupportUnit {
  schema: 'eyon.canon.causal-support.v1';
  supportId: string;
  branchId: string;
  introducedRevision: number;
  introducedByDeltaId: string;
  inputRefs: CanonCausalRef[];
  outputRef: CanonCausalRef;
  claimText: string;
  sourceRefs: string[];
}
```

语义固定为：

- `inputRefs` 内部是 AND；
- 指向同一 `outputRef` 的多个 support unit 之间是 OR；
- `claimText` 保留完整自然语言原因，不拆成关键词；
- 空 `inputRefs` 非法，直接根锚使用 `basis: direct` 表达；
- support unit append-only，退出当前世界靠所属 revision/delta 状态和重基线投影，不物理删除。

### 4.4 派生的重基线状态

```ts
type CanonOperationRebaseState =
  | 'active'
  | 'superseded'
  | 'orphaned'
  | 'uncertain'
  | 'reverted';
```

该状态应由 branch、revision、support unit 和当前事实投影按需计算，不写回覆盖旧 operation。现有 delta 的 `partially-active` 是多个 operation 状态的汇总，不替代 operation 级状态。

### 4.5 存储边界

第一版优先扩展现有 `InterventionDelta` 与 `CanonResolutionReceipt` 的可选附录，不新建第二个 IndexedDB 真相仓库：

- 新 delta 可携带本 revision 引入的 causal basis 与 support units；
- receipt 可携带本次 conflict roots、broken/surviving supports、operation states、uncertain frontier 与恢复项；
- 旧 branch 缺少 P3 附录仍可读取；
- P1 `resolveCanon` 保持纯确定性、只读、无模型、无网络，只消费已经验证的重基线投影。

## 5. 哪些关系有资格成为“确定因果”

### 5.1 可以机械传播

第一版只允许以下来源建立确定支撑：

1. 玩家行动结算中明确记录的直接前提与派生结果；
2. 已验收蝴蝶结算在同一任务中明确产出的 causal stage 关系，经短句柄解析并验证；
3. BaseCanon 中 `CanonEventRelation.relation = requires`，且关系来源为 explicit、structural 或 user-asserted；
4. 已有 `preconditionFactIds`、`dependsOnDeltaIds` 与 `originalFactIds` 所表达的现行确定依赖；
5. 后续 revision 显式声明对旧 support unit 的替代、恢复或接续。

### 5.2 不能机械传播

以下内容只可作为模型创作参考或 hypothesis：

- `before/after` 时间关系；
- inferred 且未被结算确认的 `requires`；
- 传记或墟境中的修辞性“因此”；
- 同一段落里的共现；
- 同年、同地或同一组织；
- 宏观战争、灾荒、政策、气候等未明确接入结果前提的背景；
- 模型对人物动机的合理猜测；
- 旧正文中没有绑定的因果叙述。

### 5.3 缺少因果记录不等于没有原因

如果旧 operation 没有 support unit：

- 未被冲突触及时继续按当前规则存在；
- 被精确冲突触及时进入 `opaque/uncertain`；
- 不从旧长文中用关键词反向造边；
- 不因缺字段整批报错；
- 不自动把该 operation 或整个旧 delta 判废。

## 6. P3 启动门

### 6.1 必须同时满足

P3 运行必须满足：

1. 当前输入正在产生新 revision，或正在回滚既有 revision；
2. branch、parentRevision、action/delta 身份完整；
3. 至少存在一个可机械证明的冲突种子；
4. 种子能够命中已有 fact、operation、delta 或 support unit；
5. 受影响对象属于同一 branch。

### 6.2 无冲突快速路径

若不存在冲突种子：

- P3 返回 `no-conflict`；
- 不遍历无关 support unit；
- 不调用模型；
- 不改变任何旧 delta 或产物 assessment；
- 正常提交新 revision；
- receipt 只记录 no-op 原因和零影响计数。

这是第一优先级性能与安全门。

## 7. 确定性局部重基线算法

### 7.1 输入

- parent revision 的不可变 branch 快照；
- 待提交的新 action/delta，或待回滚的 message/revision 集；
- 当前分支已有 causal basis/support units；
- 与受影响端点有关的 BaseCanon facts 与 `requires` 关系；
- P2-A 已有 operation/fact 绑定，仅用于影响报告，不参与创造因果。

### 7.2 计算顺序

```text
1. 验证 branch / revision / action / delta 身份
2. 在内存中构造候选新状态，不先写库
3. 计算 changed facts / changed operations / reverted deltas
4. 由稳定引用建立反向依赖索引
5. 找出冲突种子
6. 只从种子沿确定支撑向下遍历
7. 逐结果检查全部替代支撑
8. 得出 active / superseded / orphaned / uncertain / reverted
9. 在 uncertain 边界停止传播
10. 重新投影受影响 facts、passages、人物状态与 P2 assessment
11. 校验不变量与回滚可恢复性
12. 一次事务发布 branch + receipt；失败则旧 branch 原样保留
```

### 7.3 support unit 判定

对每个 support unit：

- 所有 input 都 active：`satisfied`；
- 任一 input 明确 inactive/reverted/superseded/orphaned：`broken`；
- 没有明确 broken，但至少一个 input 无法判定：`uncertain`。

对每个 supported output：

- 任一 support `satisfied`：output `active`，传播停止；
- 没有 satisfied，但存在 uncertain：output `uncertain`，传播停止；
- 全部 support `broken`：output `orphaned`，继续向下传播；
- 被后续同作用域 operation 明确取代：output `superseded`；
- 所属 revision 被回滚：output `reverted`。

### 7.4 delta 汇总

- 全部 operation active：delta `active`；
- active 与非 active 混合：delta `partially-active`；
- 全部被明确取代：delta `superseded`；
- 全部失去上游支撑：delta `orphaned`；
- revision 回滚：delta `reverted`；
- operation 中存在 uncertain 时，不把 delta 整条伪装成已确定；receipt 必须列出 uncertain，普通当前视图只消费安全子集。

## 8. 断裂、幸存、接续与新方向

### 8.1 因果断裂

例：

```text
[A 玲山死亡 + B 账册焚毁] → C 丑闻未公开
C → D 琉璃塔未建立
D → E 帝国新闻界衰退
```

后续 revision 使 A 失效：

1. 支撑 `[A+B] → C` broken；
2. 若 C 无其他支撑，C 是第一个断裂点；
3. D、E 依次检查；
4. 如果 D 另有独立支撑，则传播在 D 停止；
5. 不触碰任何未由 C/D/E 明确连接的事实。

### 8.2 替代支撑与幸存

```text
S1：[玲山死亡 + 账册焚毁] → 丑闻未公开
S2：[审稿官压稿] → 丑闻未公开
```

玲山获救后 S1 broken，但 S2 satisfied，故“丑闻未公开”继续 active。P3 receipt 必须显示：旧支撑断裂、结果经替代支撑幸存，而不是把它误写成“不受影响”。

### 8.3 恢复原路径

只有后续 revision 明确恢复原输入对象与适用范围时，原 support unit 才能重新 satisfied。仅仅出现相似名称、相同结果文案或另一份同类物件，不能自动复活旧支撑。

### 8.4 建立替代路径

后续干涉可以为旧结果增加新的 support unit：

```text
旧路径：[玲山持有原账本] → 揭露丑闻
新路径：[另一记者持有副本] → 揭露丑闻
```

新 support unit 必须引用新的稳定输入并保留完整 `claimText`。它接管同一结果，但不能改写旧支撑的历史存在。

### 8.5 产生新方向

如果旧结果失去支撑，而新干涉产生了不同结果：

- 新结果必须由当前 revision 的新 operation 表达；
- 旧 operation 保留为 orphaned/superseded 历史；
- 不在原 operation 上覆盖写入新文案；
- 不因为新旧结果文本相似就自动视为同一事件。

### 8.6 与其他因果区域纠缠

纠缠不新增“跨链”类型。新的 support unit 可以同时引用多个历史区域的端点：

```text
[地下情报网建立 + 军方走私网络仍存在]
→ [玲山卷入新的政变]
```

未来任一输入失效时，只重算该 support unit 及其可达下游。另一区域中没有显式输入关系的事实不受影响。

## 9. 时间、版本与持续状态

### 9.1 两条时间轴必须分开

- `revision`：玩家第几次改变历史；
- `effectiveTime`：变化在世界内从何时起发生。

后提交的 D3 可以发生在 D2 之前的世界时间。重基线顺序由 revision 决定“谁修改了当前历史”，由 effectiveTime 和状态区间决定“世界中哪些时段受影响”。不得只按数组顺序或年份排序覆盖。

### 9.2 已发生事件不可被后来条件倒删

例：

```text
407年：账本被救下
408年：琉璃塔已经成立
409年：账本再次被毁
```

409 年毁账本不能抹除“408 年琉璃塔成立过”这一 occurrence；它只能影响：

- 409 年后的证据持有状态；
- 报社持续经营；
- 后续报道能力；
- 组织归属、公开/地下状态等后续转移。

只有明确 retcon“账本从未被救下”或更早时间的变化，才可能重新打开成立事件本身。

### 9.3 状态区间

监禁、任职、婚姻、伤病、迁徙、物件持有、组织归属和机构营业均按：

```text
发生事实 + 持续区间 + 后续转移
```

处理。P3 只在后续转移与既有区间或明确因果发生冲突时介入，不创建封闭状态枚举表。

### 9.4 时间倒置与循环

- 原因在世界时间上晚于结果时，不直接硬拒绝；若世界书或玩家行动明确支持逆因果/时间法则，可保留。
- 没有这种明确依据时，该 support unit 局部 `uncertain`。
- 同一时空端点形成自依赖或闭环且无法由不同 occurrence 时间拆开时，隔离该局部循环，不发布为确定支撑。

## 10. 背景事实与 P3 的边界

战争、灾荒、气候、政策、宗教运动或行业环境默认是统一检索材料：

```text
当前有效 Canon 背景
→ 传记 / 谱系 / 墟境 / 蝴蝶 / 正文按任务相关性读取
→ 模型在创作时合理考虑
```

P3 不为这些背景建立自动传播。只有当某个结算明确形成：

```text
战争导致印刷设备征用
印刷设备征用是报社无法公开成立的必要前提
```

“设备征用 → 无法公开成立”才进入确定支撑。单独的“408 年发生战争”不触发报社因果重算。

## 11. `canon-reconcile` 的有限职责

### 11.1 不是默认步骤

以下情况完全确定时禁止调用模型：

- 单一支撑 broken 且无替代路径；
- 替代支撑仍 satisfied；
- 明确 replace/retract；
- rollback 后原支撑恢复；
- 新 delta 与旧因果无冲突。

### 11.2 准入条件

只有同时满足以下条件，才允许一次有界 `canon-reconcile`：

1. 已经存在明确冲突种子；
2. 确定性传播已经把范围缩到最小局部子图；
3. 子图内至少一个结果无法在 keep/retire/reconnect 间机械裁决；
4. 新玩家行动或本次蝴蝶结算确实需要为该局部生成一致的后续结果；
5. 输入不包含完整世界书、完整聊天或无关产物；
6. 一次调用足以表达，最多允许一次结构 repair。

P3 不为了“历史看起来更完整”主动调用模型填洞。

### 11.3 模型输入

只允许提供：

- 玩家本次行动原话；
- 冲突种子的短句柄；
- 受影响子图中 active/inactive/uncertain 的局部事实；
- broken、surviving support 的完整自然语言 `claimText`；
- 必须保留的直接行动根锚；
- 时间、地点、人物身份与当前 revision；
- 本次检索已获得的相关背景事实，但背景不自动成为硬因果。

### 11.4 模型输出

模型只能提交局部提案：

- 保留某个列出的结果；
- 退休某个列出的结果；
- 用本次新 operation 替换某个结果；
- 为列出的结果增加一条替代支撑；
- 声明证据不足，保留 uncertain。

模型不得：

- 回填内部 factId/deltaId；
- 改写玩家行动；
- 修改局部子图之外的事实；
- 引入未在输入中出现的既有人物或组织作为确定主体；
- 让后果反向否定 direct 根锚；
- 把背景可能性直接升级为硬因果；
- 无 sourceRefs 生成永久 Canon；
- 输出整条新世界史。

### 11.5 解析与失败

- 模型使用任务级短句柄；脚本恢复稳定 ID；
- 每条提案单独归一化、解析和校验；
- 坏句柄、越界对象、错误引用或无来源提案只丢弃该项；
- 一次 repair 仍失败时停止，不重试长循环；
- 确定部分照常发布；无法裁决的局部进入 uncertain；
- 不因 reconcile 失败让遣返、回滚或整个 Canon 结算报错截断。

## 12. 安全发布、审计与回滚

### 12.1 原子发布

提交前全部在内存候选分支上完成：

- 新 action/delta；
- causal basis/support units；
- operation rebase states；
- CanonResolutionReceipt；
- 受影响 ArtifactCanonAssessment 摘要。

通过验证后在一个 IndexedDB readwrite transaction 中写入同一 branch。事务失败时保留旧 branch，不能留下“新 action 已写入、旧因果未重算”的半状态。

### 12.2 append-only

- 旧 action、delta、operation、support unit 和 receipt 不物理删除；
- superseded/orphaned/reverted 只退出普通当前视图；
- 显式比较或诊断仍可查看其历史；
- P3 不修改旧产物正文。

### 12.3 回滚

回滚某 revision 时：

1. 使该 revision 引入的 action/delta/support units 退出当前候选；
2. 重新评估此前 broken 的 support units；
3. 恢复重新 satisfied 的旧结果；
4. 重算 affected P2 assessments/consumption decisions；
5. 收缩 Canon Memory；
6. 保留无关 revision 和另一分支不变。

恢复必须由同一纯函数重算得到，不能靠手工把旧状态改回 active。

### 12.4 中间 revision 回滚

删除较早 revision 时，不再简单把所有后来 revision 永久孤儿化：

- 明确依赖该 revision 的后继 operation 进入重基线；
- 有独立支撑的后继 operation 可继续 active；
- 无支撑者 orphaned；
- 关系不清者 uncertain；
- 后继玩家直接行动仍保留审计，不能因为上游删除而被当作“从未发生”。

## 13. 与现有模块的接合

### 13.1 P1 `resolveCanon`

- 保持纯确定性、无模型、无网络；
- 普通视图只应用 operation rebase state 为 active 的安全子集；
- uncertain 不混入 active，也不伪装为 inactive 的确定事实；
- BaseCanon 与 passage span 遮蔽机制继续复用。

### 13.2 P2 产物绑定与状态

- ArtifactCanonBinding 不重建；
- operationRef 得到新的局部 rebase 状态后，P2-B 按现有绑定重新派生；
- 只依赖 orphaned/superseded operation 的单位退出自动复用；
- 同产物无关单位保持 current；
- uncertain 继续 `manual-review`，不自动删除或隐藏。

### 13.3 四模块生成

- 四模块只读同一 branch/head 的 CanonResolvedView；
- P3 不增加每次普通传记、谱系或墟境生成的模型调用；
- 没有冲突时，四模块 prompt、检索排序和正文完全不变；
- 墟境仍可通过正常检索读取战争等背景，不需 P3 特殊通道。

### 13.4 Canon Memory

- 只注入当前 active 的 action/operation 简报；
- superseded/orphaned/reverted 不进入普通正文；
- uncertain 不作为确定事实注入，可在工作台诊断查看；
- 回滚后随当前重基线结果恢复或收缩。

## 14. 失败降级规则

| 故障 | 降级方式 | 禁止行为 |
|---|---|---|
| 单个 support 引用不存在 | 丢弃该 support，相关 output 为 opaque/uncertain | 整批结算失败 |
| 单个 sourceRef 截断或过期 | 局部丢弃并诊断；玩家 `chat:` 行动来源仍是硬门 | 模糊猜测相似来源 |
| 旧 delta 无 causal basis | 未触及时照常；精确冲突触及时 uncertain | 默认 direct 或整条判废 |
| 图中出现循环 | 隔离循环子图为 uncertain | 无限遍历或随意选一边 |
| 模型输出坏句柄 | 丢弃该提案 | 重跑整篇蝴蝶正文 |
| reconcile 超时/失败 | 发布确定性安全子集，局部 uncertain | 阻断遣返或混入半成品 |
| 事务写入失败 | 保持旧 branch 不变并允许重试 | 留下半新半旧 revision |
| 影响范围超过预算 | 停在边界并标记 bounded-overflow | 全库扫描或静默截断 |
| 跨分支引用 | 拒绝该局部引用并诊断 | 借另一聊天事实补链 |
| 同名但身份不明 | 不连接，保留为不同端点或 uncertain | 按名字合并人物/组织/事件 |

## 15. 性能与边界预算

### 15.1 不扫描世界

P3 只遍历：

- 新 revision 的 changed refs；
- 反向索引可达的 support units；
- 每个结果的替代 support units；
- 一层停止边界，用于证明传播已停止；
- P2 中实际绑定到这些 operation/fact 的局部单位。

不读取完整世界书，不扫描未绑定旧正文，不遍历无关传记、谱系或墟境。

### 15.2 初版安全上限

建议第一版冻结以下保护值，实施前可由自动化基准校准：

- 单次受影响 causal endpoint：最多 512；
- 单次 support unit：最多 1024；
- 单次 reconcile：最多 1 次模型调用 + 1 次结构 repair；
- reconcile 只包含受影响子图与一层边界，不携带完整语料；
- 超限不报错截断，改为局部 `uncertain: bounded-overflow`。

### 15.3 幂等

同一 runId/messageId 重试必须：

- 不重复创建 revision；
- 不重复创建 support unit；
- 不改变 stable supportId；
- 得到语义等价的 operation states 与 receipt；
- 重新生成失败后仍可重试 P3，而不是永久跳过蝴蝶链路。

## 16. 只读诊断与工作台展示

P3 第一版不新增编辑器，只扩展当前“数据管理 → Canon 局部状态”只读诊断：

- 本次是否触发 P3；
- `no-conflict` 或 conflict root 数量；
- broken support；
- surviving alternative support；
- 传播停止点；
- active/superseded/orphaned/uncertain/reverted operation 数量；
- 是否调用 reconcile、调用与 repair 次数；
- bounded-overflow/cycle/opaque 等失败原因；
- 受影响产物局部单位；
- 回滚后恢复的 support 与 operation；
- 无密钥 JSON 导出。

每个自动修正必须能回答：

1. 哪个确定前提改变了；
2. 哪条支撑因此断裂；
3. 哪个结果失去全部支撑；
4. 哪个结果因替代支撑幸存；
5. 传播在哪里停止；
6. 哪些项目无法确定；
7. 回滚会恢复什么。

## 19. 风险与预防账本

| 风险 | 典型错误 | 预防 |
|---|---|---|
| 整条 delta 粗暴失效 | 一个 operation 冲突，整次穿越全部删除 | operation 级状态 + delta 汇总 |
| 把共现当因果 | 同段/同年/同地自动接线 | 只认稳定依赖引用 |
| 把背景当硬原因 | 战争自动判定报社不能成立 | 背景走正常检索，明确接入后才成 support |
| 替代原因丢失 | 一条路径断裂就删除结果 | 同结果多 support OR 判定 |
| 多前提被拆错 | A 或 B 被误写成 A 且 B | 一个 support 内 AND，多 support 间 OR |
| 事件与状态混淆 | 后来毁账本导致报社从未成立 | occurrence 与持续区间分离 |
| 后果反向改写行动 | 模型认为结果不合理便否定玩家行为 | direct 根锚不可被下游推翻 |
| 旧数据被误判 | 缺 causal 字段即视作无依赖 | 默认 opaque，触及时 uncertain |
| 模型重新统治 Canon | reconcile 重写整条历史 | 最小子图、短句柄、一次调用、逐项校验 |
| 结构化报错截断 | 一个坏引用使遣返失败 | 单 support/单提案局部丢弃 |
| 回滚半恢复 | delta 恢复但产物/记忆未恢复 | 同一纯函数重算 + 原子事务 |
| 跨分支串线 | 同名人物在另一聊天被接入 | branchId 是第一身份硬门 |
| 时间顺序误判 | 后提交事件被当作世界中更晚 | revision/effectiveTime 双轴 |
| 循环传播 | A→B→A 无限重算 | visited + SCC/循环隔离为 uncertain |
| 性能爆炸 | 一次战争重算整个帝国 | 冲突种子 + 可达子图 + 硬上限 |
| 重试重复写入 | 同楼 reroll 产生重复 support | run/message 幂等键 |
| P3 偷渡 P4 | 自动统一所有传记、谱系内容 | 只提供 operation 状态，旧产物仍由 P2 消费 |

## 20. 四态决策账本

### confirmed

- P3 只解决确定因果冲突；无冲突内容不评断。
- 因果链是派生路径，因果支撑单元是插拔单位。
- 单 support 内 AND，同结果多 support 间 OR。
- 背景事实默认通过普通检索进入创作，不进入 P3 自动传播。
- 后来状态变化不能抹除已发生事件。
- 玩家直接行动是根锚。
- 不确定边界停止传播，不让模型静默创造唯一正史。

### implemented / frozen in P3-A/P3-B/P3-C

- 第一版复用 fact/action/operation 作为端点，不新建事件数据库。
- causal basis/support 作为现有 delta 的可选附录，不新建 IndexedDB store。
- P3-A/B/C/D 四道独立门；P3-C 只有真实需要时才启用。
- 初版遍历保护值为 512 endpoint / 1024 support。
- 旧数据缺 causal basis 时使用 opaque 兼容语义。
- P3-B 已把确定性支撑投影接入 commit/rollback 候选事务，并让 P1/P2/Canon Memory 消费 active 安全子集。
- 中间 revision 回滚只重算有明确依赖的最小子图；无依赖后继不再因修订顺序被连坐。
- 确定性路径模型调用严格为 0；P3-C 只在脚本已确定的最小 unresolved 前沿调用一次，失败局部 uncertain 且不截断发布。

### retained questions outside P3 acceptance

- BaseCanon `requires` 中 inferred 关系是否永不晋升，还是允许经玩家确认晋升；
- P3-C 超时或 repair 仍失败的真实宿主故障样本未人为制造；其降级语义已由自动化 CR-21 覆盖，不作为 P3 验收阻塞项。

### rejected

- 建立宏观“背景影响场”并主动重算全世界；
- 持久化整条不可拆因果链；
- 通过固定关键词从旧正文反向抽因果；
- 每次干涉调用模型重写全部历史；
- 为 P3 建立平行 Canon/Timeline 真相仓库；
- 用复杂结构字段替代玩家原话和完整因果说明。
