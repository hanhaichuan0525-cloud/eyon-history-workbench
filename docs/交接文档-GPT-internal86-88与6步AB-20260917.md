## 二、这一批做了什么（机制级）

### internal.86 · 蓝图 §6 步 A：蝴蝶记忆注入通道

**问题**：改写后的历史此前只在**生成任务内部**可见（`<CANON_CURRENT_VIEW>`），普通聊天正文收不到 → 模型会接着写"已被改写掉的人还活着"。

**做法**：新增 `src/runtime/canonMemoryChannel.ts`，把"当前分支仍有效的改写历史"做成**独立注入通道**：

- 有效性判定与 P2-B 评估同源（记录级 + delta 级确定性子集，不依赖检索 Bundle）；
- 分层（§6.4）：**常驻**＝当前有效序列最近 1~2 条（必然相关）；**触发式**＝更早仍有效者按关键词命中；总预算 2400 字、单条摘要 320 字；
- 注入走 ST `setExtensionPrompt`（key `eyon_canon_memory`、in_chat、depth 0、system），块体 `<CANON_MEMORY branch revision>`；注入空串＝清除（幂等）；
- 刷新时机：生成前（`generationAfterCommands`）/ 切聊天 / AI 楼渲染后 / 删楼 / 手动重算；dispose 清空；
- 匹配源＝最近 8 楼可见正文 + 玩家当前输入（读取失败降级为空匹配，不阻断生成）。

**工作台诊断面板**（驾驶员明确要求"留可查验的口子，一目了然"）：「数据管理 → 蝴蝶记忆注入」——状态徽章（`注入中 · N 条` / `未注入（无有效条目命中）`）、revision + 触发时机 + 时间戳、计数（总/常驻/触发/未命中/已失效）、失败行、注入全文折叠、逐条判定（硬/软关键词、命中词、入选原因）、「重新计算」「导出诊断 JSON」。

## 八、这批交付里最值钱的"验收方法"教训（给后续会话省时间）

1. **判据会被消耗**：一旦某个"注入独有词"被模型写进正文，它就永久留在上下文里，不能再当判据（本批烧掉了 `兄弟会`、`铁律`）。判别注入时必须先**diff 出"只在注入块里出现过的词"**，并预留后续判据。
2. **镜像双注入会毁掉归因**：镜像世界书（完整档案）与 `CANON_MEMORY`（简报）内容重叠时，"后续正文延续"无法归因。本批靠**驾驶员正好取消挂载镜像的窗口**才完成归因——这也是步 B 要退役镜像的实证理由。
3. **上下文惯性 ≠ 注入生效**：改写内容一旦被正文复述，就成为独立载体；因此"续写是否延续"**单独不能证明通道生效**。
4. **常驻层让"零注入"不可观测**：`RESIDENT_LIMIT = 2` 使最近 1~2 条恒注入，面板「未注入」只在**一条有效档案都没有**时出现；"旧史不越界"应表述为"旧档案不因无关话题被拉入"。
5. **状态字段要与唯一真源对账**：G-12 的根因是"副本状态没人维护"——凡是有副本状态（`canonStatus`、镜像条目、缓存快照），都要有**幂等对账**而不是依赖"谁触发谁负责"。
