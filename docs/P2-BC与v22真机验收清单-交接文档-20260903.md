## Part A · internal.81 v22 真机复验（同楼跨 run 版本回滚收口）

> 病历回顾：楼 52 被多次重结算复用，run A 与 run B 的 delta 并存 active，删楼回滚旧实现只 retire 最新一条，旧 run delta 成为永远 active 的孤儿 → artifact 评估悬成 uncertain。v22 修复：删楼 = 该楼承载的全部蝴蝶/穿越版本（跨 run）进入历史。
> 若上午的现场已不在（已删楼或开新聊天），用 A3 造一个新现场后执行 A4。

**A1 · 复用楼删除（核心断言）**
- 操作：在**现有现场**（若 3 条 uncertain 与楼 52 仍在）删除那栋被复用的遣返正文楼（或最新一次遣返正文楼）。
- 预期：刷新 Canon 局部状态后——
  - 该楼承载的**全部** active revision（跨 run，含 run A 与 run B、R5「当前有效」）进入 `reverted` 历史，不再有跨 run 幸存 active；
  - 「待人工判断·不自动判废」的 uncertain artifact **收敛为 0**（或只剩与本楼无关的真实不确定项），不再出现「删了楼还挂在 active 的孤儿」；
  - 导出 JSON：receipt 的 `revertedDeltaIds` 同时含两条 run 的 delta（v22 语义：删除一栋楼 = 该楼全部版本进入历史）。
- 对照断言：AS-05（仅真 orphaned 才判 orphaned）、v22 病历「遗留 R2 孤儿 delta 即被自动收口」。

**A2 · 重走一轮全链路**
- 操作：进墟境 → 执行一次历史干涉（任何行动，规模不限）→ 输入「遣返」走正常楼层。
- 预期（v19 真机已全绿、v22 后应保持）：
  - 正文一次成功（非 DeepSeek 中转下单请求约 15–30 秒，**不再出现 4 分钟级卡死**）；
  - 蝴蝶面板出现在**遣返正文之后、MVU 变量面板（`<UpdateVariable>`）之前**，MVU 面板固定在楼尾（v20）；
  - 现实时间地点恢复（v19 病历现象「终于成功了，现实也返回了」）；
  - 只形成 **1 条新 active revision**；时空页无残留 pending、无「蝴蝶效应尚未归档」悬浮框。
- 对照断言：v15（冻结体量 ≤1500/请求 <40KB）、v16（20–400 容忍窗）、v20、v21 语义回归。

**A3 · 删楼重掷语义（v21 收口确认）**
- 操作：对刚完成的那一轮做两种玩家常态操作，各一次：
  1. 直接重掷（regenerate）正文 → 新变体楼里应自动补插同一份蝴蝶面板（幂等，不重复、不入账两次）；
  2. 删除该遣返玩家楼或 AI 楼后，同句再发「遣返」→ 应**重新冻结并生成新版**（不再复用被回滚的旧文本，`canonStatus='reverted'` 记录不复活）。
- 预期：Canon 局部状态里 revision 链 append-only 且状态正确（`reverted` / `active` 交替符合操作顺序），无「档案永远指向已回滚 Canon」的死结；普通聊天消息全程不触发蝴蝶准备（v14 只认 `ruin.return`）。

**A4 · 幂等与清理出口（v17/v19 功能点真机收口）**
- 操作（任一失败 pending 现场，或 A2 之后故意中断一次）：
  1. 时空页出现「待重试」条目：详情顶部**带失败原因**，点「重新归档」有明确成功/失败悬浮反馈；
  2. 设置页 → 清理生成缓存：确认文案含「…与未归档的蝴蝶效应结算快照」，结果提示带 `蝴蝶待结算 N` 计数，且**已归档蝴蝶记录不受影响**。
- 预期：失败不再无声、不再「干脆什么悬浮框都不显示」（v19 病历）；失败原因能指向卡在哪一步（面板/镜像/Canon）。

## Part B · P2-B/P2-C 合并真机验收（NEXT.md §5 五步门）

> 观察出口已可用：**设置页 → 数据管理 → Canon 局部状态**（当前 head / active / reverted / orphaned revision、actionRecord、delta operation 数、局部消费结论、导出无密钥 JSON）。以下每场都按「造 revision → 刷新观察 → 导出」执行。造 revision 的唯一路径 = 真实干涉（进墟境执行行动 → 遣返 → 蝴蝶结算），**不构造数据、不手动改存储**。
>
> **防混淆（P1-1 §三.2 分工，后人勿犯）**：历史有两层通道——**档案层 = 代际替换**（删旧传记档案→生成新档案，无机制自动仲裁，P1-1 三剧本用此法）与 **canon 层 = delta 遮蔽**（穿越→遣返→蝴蝶结算的正式提交链）。本 Part 验的是 **P2-B/P2-C 的 canon 层五态**，因此**禁止用「删传记档案」冒充干涉 revision**——那不走 action/delta 链，测不到任何 AS/PC 断言。
>
> **上下文即世界（P1-1 §三.3）**：聊天历史中的旧正文是模型的强依据。建议 Part B 每场在干净环境执行（新聊天，或用后清掉依赖楼），避免旧文本把新干涉带偏；脚本层五态评估不依赖正文质量，但正文是制造干涉的手段，正文被旧语境污染会导致结算内容与剧本意图不符。

**场景 1 · 无关 revision 不动旧产物（NEXT 第 1 步；AS-02 / PC-02）**
- 操作：做一场**与既有已绑定产物无关**的新干涉（不同对象或不同时期，例如另一名角色/另一处地点的事件），遣返结算。
- 预期：刷新 Canon 局部状态后——
  - 旧产物的绑定单位保持 `current`（评估）与 `available`（消费），**「版本变新」本身不构成失效**；
  - 设置页只新增 1 条 active revision，旧 action/delta 原样在历史中；
  - 旧正文（已生成的传记/墟境/面板）逐字不变。
- 反证记录：全程无新增模型请求（除新干涉自身的正常生成外）；普通聊天正文里没有蝴蝶日志混入。

**场景 2 · 替换既有绑定事实 → 只影响依赖者（NEXT 第 2 步；AS-03/AS-04 / PC-03/PC-04）**
- 操作：对**场景 1 之前某个已绑定产物依赖的事实**做新干涉——用同一对象再走一轮，行动内容与该产物依赖的事实冲突/替换（例如：先写「尤娜死于极光爆发中的扼杀」，再走一轮把它改写为「死于魔力过载事故」的 verified replace，或对同一人的同一事实做 retract）。
- 预期：刷新后——
  - 只依赖被替换事实的单位 → `partially-stale`（部分）或 `stale`（全部）→ 展示为 `available-with-warning` 或 `excluded`；
  - 同产物中**未绑定该事实的兄弟单位**保持 `current/available`（局部失效不封杀整段、不整批回退）；
  - 旧正文原稿**不被改写**（翻旧楼核对原文）；
  - 无关 revision / 无关单位不误判（对照 AS-03 同产物兄弟单位、PC-03 单单位部分失效语义）。
- 若只想做最小代价的替换：一场即可，但要记录被影响单位 id 与兄弟单位 id。

**场景 3 · 删除/回滚干涉楼 → 原单位恢复（NEXT 第 3 步；AS-09 / PC-08）**
- 操作：删除场景 2 的那栋干涉（遣返）楼，刷新 Canon 局部状态。
- 预期：
  - 先前 `partially-stale/stale/orphaned/uncertain` 的单位**重新计算为 `current/available`**；
  - 恢复**无需清缓存、无需重生成**（P2-C 直接从 branch head 重建投影）；
  - 绑定原稿与旧 assessment 均不被改写（历史审计链完整）；
  - 场景 2 的 revision 进入 `reverted`，receipt 列出其 delta。
- 对照断言：AS-09「回滚恢复 current 不改写绑定」、PC-08「刷新即恢复」。

**场景 4 · 导出核对与确定性（NEXT 第 4 步；PC-09/PC-10）**
- 操作：全流程结束后导出最终 JSON，并连续刷新两次设置页。
- 预期：
  - 导出 JSON 与界面汇总一致：`branchId/headRevision`、actions/deltas/receipts/counts、revisionStatuses/deltaStatuses 逐项对得上；
  - 相同 branch + bindings 重复刷新 → 投影、assessment、decision 与排序**确定性等价**（PC-10）；
  - 导出文件不含 API 密钥/凭据（有界报告：变更 ≤128 条、assessment/decision ≤512 条）。

**场景 5 · 全程约束确认（NEXT 第 5 步）**
- 逐场勾选：①无新增模型请求（除各场自身生成外，删除/刷新/导出/翻旧楼零请求）；②蝴蝶日志没有以任何形式偷塞进普通聊天正文（G-03/G-08 边界不因本验收被越过，P1-1 §四「严格版不可用正文可见性伪装验收」守则沿用——本验收只观察 canon 层日志与只读展示，不宣称正文注入已验）；③普通检索/生成不被 excluded/manual-review 物理裁剪（P2-C 只读展示与消费结论，不接入普通生成源的细粒度裁剪——本验收不打开那道门）。

**场景 6（可选）· 分支隔离快检（AS-08 / P1-1 剧本 3 延伸）**
- 操作：场景 3 全部通过后，另开一个聊天 B 做一场无关干涉并结算；随后切回原聊天 A 刷新 Canon 局部状态。
- 预期：A 的 branch/head/revision 与场景 3 结束时完全一致（跨分支不串线、不借用 B 的事实给 A 的状态）；B 的干涉不出现在 A 的变更日志里。
- 说明：分支隔离在 P1-1 RC-07 已真机验收、AS-08 已有自动化覆盖，本场景为合并验收的加强快检，时间紧可跳过并标注 N/A。
