# 职责

本文件只规定脚本如何把界面结果交给正文模型，以及如何在明确遣返时协调正文、时间控制模块与后台蝴蝶效应结算。

职责:

- 墟境内叙事、遣返叙事与变量更新继续由现有世界书规则负责；任务草案由脚本按玩家方向独立生成，但只经正常正文楼落入 MVU。
- 现实、进入、当前、离开时地及状态切换继续由现有时间控制模块负责。
- 蝴蝶效应内容由独立API生成，脚本校验、排版、追加并归档。
- 正文模型不得再自行生成第二份蝴蝶效应面板。

# A. 单楼选定并进入

玩家在界面选中候选和缘起、经过、高潮或结果节点并点击“进入此节点”后，脚本从已校验的结构化结果生成唯一 `ruinTraceRaw`，并在同一次玩家发送中提交进入契约。候选的后台生成、切换和浏览不创建聊天楼；只有点击“进入此节点”才创建一条玩家楼。

本流程固定为:

```text
玩家楼: 进入节点 + 单楼进入契约 + 唯一RuinTrace
紧邻助手楼: 承接上一楼现实剧情 -> 自然穿越 -> 只建立墟境现场与唯一完整变量更新（不生成任务）
```

不得再创建“先展示候选面板、下一楼再次进入”的中间确认楼。

## A.1 RuinTrace

`ruinTraceRaw`只生成语义原文，不生成HTML。

固定序列化格式:

```text
[RuinTrace]
Title:: {{candidate.title}}
Type:: {{candidate.periodType}}
Span:: {{candidate.span.label}}
History:: {{candidate.historyProse}}
Shift:: {{candidate.shift}}
NodeTime:: {{node.time.label}}
[/RuinTrace]
```

约束:

- 字段名、双半角冒号、字段顺序和首尾标签必须完全一致。
- `Type` 只能是 `稳定期`、`过渡期` 或 `动荡期`。
- 任一字段内容中的换行可以保留，但不得生成第二组同名字段或第二个 `[RuinTrace]`。
- `ruinTraceRaw` 必须由脚本从结构化JSON确定性生成，不允许正文模型或美化正则反向修改。
- `Type` 与 `Shift` 中的时期名称必须使用中文显示值，不能把 `stable|transition|turbulent` 暴露给正文或美化。

## A.2 发送前硬校验

脚本只有在以下条件全部成立时才允许发送:

1. 候选记录存在于当前 `characterKey + chatId` 的本地命名空间。
2. 候选和节点ID能够在该已校验记录中唯一找到。
3. 节点为 `origin|process|anomaly|result` 之一，候选状态为 ready，且存在明确介入机会与至少一条可能分支；旧记录中的 `enterable=false` 不再封死非高潮节点。
4. 当前墟境流程状态严格为 `idle`。
5. 点击瞬间能够读取非空的现实时间与现实地点。
6. 发送前再次核对聊天命名空间没有变化。

任一条件失败时不发送半截命令，不创建玩家楼，不改变量。

## A.3 唯一玩家楼

脚本发送下列确定性文本:

```text
进入节点

【历史工作台·单楼进入契约】
现实锚点时间：{{clickTimeReality.time}}
现实锚点地点：{{clickTimeReality.location}}
目标纪元：{{response.era}}
目标墟境时间：{{node.time.label}}
目标墟境地点：{{resolvedNodeLocation}}
史案标题：{{candidate.title}}
历史阶段：{{origin=缘起|process=经过|anomaly=高潮|result=结果}}
历史节点：{{node.title}}
节点局势：{{node.summary}}
直接成因：{{node.cause}}
因果机制：{{node.causalMechanism}}
参与人物与组织：{{join(node.participants, "、") || "无明确资料"}}
利益与恐惧：{{format(node.interests)}}
物质条件：{{join(node.materialConditions, "、") || "无明确资料"}}
对立关系：{{node.opposition || "无明确资料"}}
可感知痕迹：{{node.visibleTrace}}
玩家可介入条件：{{node.intervention}}
可能分支：{{format(node.possibleBranches)}}
参与人物用途：{{format(candidate.selectedCharacterUsage) || "未指定参与人物"}}
玩家补充方向：{{supplementaryDirection || "无"}}
资料标识：{{requestId}} / {{candidate.id}} / {{node.id}}

请直接承接上一楼尚未结束的动作、人物关系与现场氛围，自然描写从现实锚点进入上述历史节点的过程；不要把史稿复述成说明书。进入完成后，按现有伊雍墟境任务与变量规则，在本楼建立唯一新轮次、锁定现实锚点、把目标时地写入世界与墟境当前时地，并将流程状态更新为 exploring。回复末尾只输出一份完整变量更新。

{{ruinTraceRaw}}
```

现实锚点必须在点击时读取，不能沿用候选生成时的旧世界快照。候选可以在同一聊天中稍后进入，但不能跨聊天使用。`resolvedNodeLocation` 必须是角色卡 MVU 规范的 4～8 层地点路径；`墟境当前地点`、`本轮墟境进入地点` 与 `世界.地点` 必须逐字复制该值。结果阶段只允许改变余波、证据、救援与后续传播，不得无因抹除已经发生的前史。

## A.4 正文联动

正文模型收到此玩家楼后必须:

1. 把它视为玩家已经明确选择并执行“进入节点”，而非请求再次介绍候选。
2. 承接紧邻上一楼的动作、在场人物、情绪和未完对话，描写现实场景被历史坐标接管的连续过程。
3. 不复读完整史稿，不把字段逐项解释给玩家。
4. 允许伊雍依据现有核心自然说话；脚本不代写伊雍台词。
5. 以契约中的现实锚点冻结本轮现实时间地点。
6. 以目标墟境时地建立本轮进入时地、当前时地和世界时地。
7. 新建唯一墟境轮次，设置任务规则锁，状态写为 `exploring`。
8. 在同一助手楼输出正式墟境面板及唯一完整变量更新，不等待第二条“进入节点”命令。

脚本不得在助手楼生成前抢先写 `exploring` 或覆盖世界时地。变量写入仍由正文/MVU与现有时间控制模块完成。

# B. 幂等与失败

- 同一 `chatId + recordKey + candidateId + nodeId` 的连续双击只允许发送一个玩家楼。
- 发送接口失败时允许重试；发送成功后禁止同一按钮再次发送。
- 发送成功只代表玩家楼已建立，不代表脚本自行确认变量写入成功。
- 正文或MVU更新失败时由现有变量恢复流程处理，候选生成器不得补写或猜测状态。
- 这里专指“进入墟境”的 `RuinTrace`：它不使用占位槽，也不在助手楼渲染后追加第二份 `RuinTrace`；C.1 的墟境任务卡另用请求专属占位槽原子落地，二者不得混用。

# C. 禁止隐式动作

- “墟境探索”只在后台或界面生成候选，不能进入。
- “进入节点”只由玩家点击或明确输入触发。
- “遣返”只由玩家点击或明确输入触发。
- 界面浏览、API生成、切换候选、查看族谱、打开传记都不得向正文发送状态指令。
- 脚本不得仅凭当前存在候选节点就写入 `exploring`。

## C.1 进入后的墟境任务

任务模块嵌在“墟境探查”页面内，只有 `flowState=exploring|anchored` 时显示。进入节点本身不自动建立任务；<user>可填写严肃目标，也可以只写一个轻量互动，并选择演绎权限与任务规模。

流程固定为：

```text
界面输入 + 演绎权限 + 任务规模 -> 独立 API 生成并校验 eyon.ruin-task.v1 草案
-> 工作台展示草案，允许修改任务名称、详情与目标（此时不创建聊天楼）
-> <user>确认后，脚本只把“确认墟境任务：任务名”写入酒馆输入框（不创建聊天楼）
-> <user>可继续补写本轮行动并亲自发送；发送拦截器才封缄完整玩家输入并创建正常玩家楼
-> 紧邻助手楼自然引出封缄任务 + 唯一任务卡占位槽 + 唯一 MVU 变量更新
-> 助手楼生成完成后，脚本把该槽原子替换为一份 <task_info> RPG任务卡
```

硬约束：

1. `stat_data.任务列表` 是唯一事实源；`<task_info>` 只展示同一记录。
2. 脚本不得直接改写 `任务列表`，不得和正文/MVU形成双写。
3. 任务名称固定为 `[墟境任务·个人]名称` 或 `[墟境任务·团队]名称`，记录字段严格沿用角色卡既有 `状态/关注度/进展/详情/目标/奖励`。
4. 若任务列表中已有非终态墟境任务，API 调用前即拒绝生成第二项；完成、失败、取消、放弃、终止、已结算或可结算后，仍在同一墟境时才可建立下一项。
5. “原意锁定”不得新增人物、动机、意义或期望结果；“情境补全”只补现场已有阻碍；“自由演绎”可沿已有证据增加波折，但三者都不得替<user>行动或宣布成功。
6. “即时互动”只需一两个当场动作；“短程目标”限当前或相邻场景；“阶段任务”才允许跨场景。不得把玩笑、触碰、闲逛等轻量输入拔高为训诫、拯救、改革或永久历史使命。
7. 正文可见面板由脚本将同一份封缄记录确定性渲染为 `<task_info>` 内的RPG任务卡，委托人固定为伊雍，展示`任务/委托人/等级/详情/目标/奖励`；不得输出双冒号旧格式，不得让模型自行改写CSS。MVU内部仍沿用既有六字段，不另造第二套状态。
8. 奖励固定包含脚本难度映射的FP、「明确数值Z + 实体币名」和一个与本次墟境直接相关的道具；不得使用通用G占位，也不得发放EXP。每份新草案都重新读取当前角色卡世界书的经济指南，依当前墟境地点解析势力币名，依个人/团队、难度与任务规模计算整数金额；币制无法唯一确定时必须明确拒绝，不得回退到“当地通货”。已封缄任务保留确认时原值，不随后续世界书变更漂移；轻量任务的道具应收束为纪念物、日用品或小型线索物。
9. 点击确认只进入 `staged`，不得自动发送或抢占玩家楼；只有<user>亲自发送含确认标记的输入时，才冻结 `chatId + runId + triggerPlayerMessageId + approvedTaskHash` 与完整契约。删除或重抽助手回复只重新注入同一封缄文本，不得再次调用任务API或读取当前表单；只有删除确认玩家楼才恢复为可编辑草案。
10. 聊天、轮次或任务状态在 API 返回前发生变化时，结果隔离，不创建玩家楼。
11. 任务由非终态首次变为完成、失败、取消、放弃、终止、已结算或可结算时，脚本在造成该变化的助手楼追加唯一 `<task_result>` 终态卡；样式与建立卡一致，任务列表仍是唯一事实源。若同楼同时遣返，必须先追加任务终态卡，再追加蝴蝶效应面板，避免并发覆盖。

# D. 明确遣返与后台结算

## D.1 触发

只允许两种触发:

1. 玩家点击悬浮球或完整面板中的“遣返”按钮。
2. 玩家当前输入明确要求“遣返”“返回现世”“回到现实”或“结算蝴蝶效应”；整句被 `**…**` 或 `__…__` 包裹时仍按内部语义识别。

任务完成、历史定锚、查看现实面板、提到“以后返回”或NPC建议离开均不得触发。

## D.2 按钮发送

玩家点击“遣返”时，脚本向酒馆输入框写入并发送:

```text
遣返
```

不得附加候选史稿、API提示词、冻结快照、变量路径或内部 `requestId`。

## D.3 冻结顺序

在遣返命令交给正文模型和时间控制模块之前，脚本必须调用现有归档快照器冻结:

- 当前 `characterKey`
- 当前 `chatId`
- 当前活动 `runId`
- 进入墟境前的现实时地
- 进入时墟境时地
- 离开时墟境时地
- 本轮玩家关键干涉行动
- 本轮涉及人物、组织、器具和地点
- 蝴蝶效应范围骰点与命中等级
- 触发玩家楼层ID

冻结成功后立即创建 `butterfly`请求。不得等待正文变量清空后再回读活动字段。

冻结失败时:

- 按钮不得伪造锚点。
- 明确提示缺少哪一组数据。
- 不启动蝴蝶效应API。
- 是否继续普通遣返由现有时间控制模块决定，脚本不得擅自恢复或修改状态。

## D.4 并行流程

冻结成功后允许并行:

```text
流程A: 正文模型生成遣返叙事 -> 时间控制模块恢复现实并清空活动状态
流程B: 独立API生成蝴蝶效应JSON -> 脚本校验 -> 等待绑定的遣返AI楼层结束
```

流程B不得阻塞流程A。

API失败不得导致遣返回滚，也不得让 `idle` 恢复为 `exploring|returning`。

## D.5 正文模型提示

正文遣返请求必须附带仅对正文模型可见的脚本指令:

```text
本楼按现有伊雍核心完成遣返叙事、现实时间地点恢复与唯一完整变量更新。
蝴蝶效应内容由脚本后台结算，本楼不要生成、猜测或复写 <butterfly_panel>，不要延迟遣返等待结算。
```

该指令不得出现在玩家输入框、可见正文或世界书归档中。

## D.6 面板追加

正文流式输出结束且后台结果校验通过后:

1. 精确取得本次遣返对应的AI消息ID。
2. 再次核对 `characterKey + chatId + runId + triggerMessageId`。
3. 若该消息不存在 `<butterfly_panel>`，在正文末尾追加一个固定格式面板。
4. 若旧规则或模型已经输出面板，只替换该消息中唯一的旧面板，不得重复追加。
5. 不改写遣返叙事、伊雍对白、任务结算或变量更新块。
6. 追加成功后才允许写入本地正式归档和世界书镜像。

API原始JSON、内部自检和来源索引不得写入正文。

## D.7 失败与重试

后台生成、校验、正文追加或世界书镜像任一步失败时:

- 遣返仍保持完成。
- 冻结快照与已校验中间结果按当前聊天保存。
- 状态标记为 `pending_settlement`。
- 面板显示“历史结算待重试”。
- 重试不得重新读取已清空的MVU，不得重新掷骰，不得重新生成遣返正文。

# E. 双写禁止

- 正文模型不得自行创作 `<butterfly_panel>`。
- 蝴蝶效应API不得生成遣返叙事、伊雍对白或变量更新。
- 时间控制模块不得读取蝴蝶效应API结果决定是否遣返。
- 归档脚本不得根据存在蝴蝶效应日志推断当前流程状态。
- 同一 `chatId + runId` 只允许一个完成面板和一个世界书锚定条目。
