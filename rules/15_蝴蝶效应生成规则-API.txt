# 一、机制定位

本规则只负责在一次墟境已经明确遣返后，根据脚本冻结的同轮次史料，创作该轮墟境干涉在现世造成的蝴蝶效应。

本规则不负责:

- 判断玩家是否要求遣返。
- 切换 `exploring|anchored|returning|idle`。
- 恢复或修改世界时间、地点。
- 读取、更新或清空MVU变量。
- 决定进入时、离开时或现实锚点的时间地点。
- 输出伊雍对白、遣返正文、任务奖励或变量更新。
- 直接写入聊天、世界书或本地资料库。
- 生成HTML、Markdown表格或 `<butterfly_panel>`。

遣返流程由现有时间控制模块独立完成。即使本请求失败，遣返也必须保持成功，不得回滚。

# 二、调用条件

只有脚本已经确认以下全部条件时才允许调用:

1. 玩家明确点击“遣返”，或玩家当前输入明确包含“遣返”“返回现世”“回到现实”“结算蝴蝶效应”等主动命令。
2. 当前存在合法活动 `runId`。
3. 脚本已经在清空活动字段之前冻结同一轮次的完整归档快照。
4. 现实锚点、墟境进入点和墟境离开点均为完整时地对。
5. 本轮至少存在一项可确认的玩家墟境行动。
6. 蝴蝶效应范围骰点已经由脚本产生并映射完成。

不得因为正文提到“返回”“离开”“现实”等普通叙述而调用。

不得因为任务完成、节点定锚、API候选生成完成或状态为 `anchored` 而自动调用。

# 四、锚点不可变

以下字段是脚本冻结的事实，不是创作素材:

- `runId`
- `anchors.reality.time`
- `anchors.reality.location`
- `anchors.ruinEntry.time`
- `anchors.ruinEntry.location`
- `anchors.ruinExit.time`
- `anchors.ruinExit.location`
- `dice.roll`
- `dice.scope`

模型不得:

- 改写、补齐、规范化或纠正这些值。
- 用墟境时地替换现实锚点。
- 用现实锚点冒充墟境进入点。
- 把进入点推进为离开点。
- 从正文另找一套“更合理”的时间地点。
- 因觉得骰点与事件规模不匹配而改变波及范围。

输出只需原样回显 `runId` 和骰点范围，不回显三套时地。三套时地由脚本直接写入最终日志。

# 五、资料权威顺序

发生冲突时依次遵循:

1. `anchors` 与脚本提供的骰点映射。
2. 当前角色卡已启用世界书的明确事实。
3. 当前聊天未隐藏、当前采用消息页中的已确认事实。
4. 本轮 `playerInterventions`。
5. 当前聊天MVU人物与世界状态摘要。
6. 当前聊天已经归档的蝴蝶效应。
7. 已保存传记中的明确资料。
8. 宗族谱系中的明确资料。
9. 为连接因果链所作的有限推断。

推断不得覆盖明确事实。资料冲突无法协调时，在 `warnings` 中说明，不得擅自选择方便创作的一方。

# 六、创作目标

蝴蝶效应必须写成一条能够追溯的历史传播链:

```text
玩家在墟境中的具体行动
-> 当时立即改变的人、物、制度或信息
-> 变化如何被保存、继承、误读、交易、压制或放大
-> 一个或多个中间历史阶段
-> 遣返后现实中的具体落点
-> 玩家现在能够感知或验证的证据
```

不能只写“玩家改变了过去，因此未来发生变化”。

不能把墟境内部结果直接复制成现世结果。

不能把几百年的演化压缩成没有媒介的一次跳跃。

## 6.1 因果账本

生成前必须在内部建立一条只读因果账本，不得输出思考过程:

1. `baseline`: 若玩家没有介入，原历史会怎样继续。
2. `firstDivergence`: 玩家哪一个已完成行动首先改变了基线。
3. `firstCarrier`: 第一位承接变化的人、组织、器物、制度或信息载体。
4. `propagation`: 变化如何被保存、继承、误读、交易、压制或放大。
5. `stoppingBoundary`: 为什么影响最终停留在骰点对应范围，而没有无限扩张。
6. `presentLanding`: 遣返后现实中的具体落点。
7. `evidence`: 玩家当前能够验证的具体证据。

`previousButterflyAnchors` 是去重索引。必须比较旧日志与本轮的首个分歧、传播载体、现世落点和影响机制。若高度相似，本轮必须明确表现为旧影响的延续、叠加、抵消或分叉；不能只替换人物名或地名后重复同一结果。

每条因果链至少保留一项阻力、代价、误读、副作用或未完全达成的结果。蝴蝶效应可以有利，但不能成为无成本、无阻力、无限扩张的单向奖励。

# 七、波及范围约束

骰点决定的是“哪个最小社会容器的正常状态被永久改写”，不是听闻消息、围观或短期受波及的人数；它不决定影响善恶，也不决定事件表面大小。新闻可以传得更远，短期反应可以越界，但稳定后真正改变的生活与制度必须停在本档范围。

- `个人`: 只永久改写一名核心人物的经历、身份、记忆、财产、身体、名誉或关键选择。他人可以目击、议论或受轻微牵连，但不得再出现第二条同等分量的人生改写，也不得升级成集体制度。
- `双人`: 永久改写恰好两名核心人物之间的关系、契约、亲缘、债务、敌意、依赖或共同秘密。第三方只能作为见证者、阻力或执行者，不能夺走两人关系作为结果核心。
- `小队`: 永久改写一个边界清楚的有限团体，例如调查队、卫队小组、家族支系、教团小组或工作单位。重点落在成员分工、内部规则、共享秘密或集体名誉，不得扩成整个聚落的共同秩序。
- `聚落`: 永久改写一个有共同生活空间的小型共同体，例如村庄、街区、庄园、城堡附属区或据点。变化应落在一处公共资源、地方习俗、建筑、权威或共同记忆上，聚落之外只保留零散回声。
- `城市`: 永久改写一座城市的制度、主要组织网络、贸易、治安、宗教、建筑或人口运行方式。可以在不同街区表现不均，但不得自动成为周边地区的普遍规则。
- `省份级地区`: 永久改写多个聚落之间共享的行政、交通、生态、产业或族群系统。必须说明它们为何被同一机制串联，同时不能把该机制写成全国默认制度。
- `国家`: 永久改写国家机器或全国尺度的法律、继承、军制、货币、宗教、经济或族群格局。国外可以回应、获利或警惕，但结果核心仍应收束在该国。
- `跨国`: 永久改写两个以上政治实体之间的贸易、战争、信仰、迁徙、外交或跨国组织网络。必须让至少两方通过同一载体持续相互作用，但不得空泛扩大为整个世界都被改变。

大行动可以因历史收束只产生小范围影响；微小行动也可以通过关键媒介扩散为大范围影响。

无论大小，都必须解释为什么最终范围恰好停留在骰点对应层级。

低骰点不是低价值：个人与双人范围应当贴身、具体，并持续影响人物选择；高骰点也不能只靠宏大旁白，必须从一个可见的人、地方或物件切入系统变化。

每条结果都应让因果链发生一次出人意料但回看后合理的性质变化，明确谁从变化中获益、谁替它付出代价，并在现世留下一个能被玩家继续调查、利用、保护、交易、对抗或误解的遗留物。这些要求必须融进自然史稿，不得写成范围说明、得失清单、游戏结算报告或固定模板。

# 八、因果媒介

优先选择与本轮史料相符的传播媒介，不要固定套用同一种模式。

可用媒介包括但不限于:

- 血缘、婚姻、收养、私生关系与继承。
- 档案、账本、地图、契约、法律、判例与行政惯例。
- 货币、债务、商路、税制、工艺、资源与产业。
- 武器、遗物、器具、建筑结构与基础设施。
- 教义、仪式、传说、禁忌、污名与集体记忆。
- 战争、迁徙、灾害、疾病、治安与军事部署。
- 师承、组织、派系、秘密网络与职位更替。
- 身体特征、种族习惯、寿命差异与超自然遗传。
- 被掩盖、误读、伪造、丢失或重新发现的信息。

媒介必须来自输入资料或受世界观约束的合理补全。

# 九、中间演化

`historicalEvolution` 应包含2至5个有功能差异的演化阶段。

每个阶段至少回答:

- 谁继承或接触了上一阶段的变化？
- 他们为什么保留、利用、误解、抵制或放大它？
- 变化通过什么制度、关系或物质载体继续存在？
- 下一阶段为何会从这一阶段自然产生？

不得机械使用“数十年后”“百年后”作为唯一连接。

不得为凑阶段数引入与玩家行动无关的宏大事件。

## 9.1 阶段必须发生“变形”

有趣的历史演变不是同一结果不断变大，而是变化在传递中改变性质。例如：

```text
一封信件 -> 一次判例 -> 一项行会制度 -> 一种地方习俗 -> 一件现世证物
```

相邻阶段至少改变下列一项：承接者、传播载体、利益关系、制度用途或社会解释。不得把“影响扩大”“争议加剧”“秩序动荡”换词重复成多个阶段。

每条演变至少写清：

- 一位承接者为什么主动保存、利用、抵制或误解变化；
- 谁从变化中获益，谁承担代价；
- 一次误读、阻力、利益转移、反转或讽刺性结果；
- 哪些原有事实没有被这条因果链触及，因而继续保持。

既有具名人物只有在资料支持、年代可用且确实承担因果职责时才能出场。缺少合适人物时使用“抄写员、祭司、矿工、行会代表”等匿名角色；不得为了让历史显得热闹而创造新的正史名人、家族成员或子嗣。

# 十、与现世联动

`presentLanding` 必须落在玩家遣返后的现实冒险能够接触的范围内。

落点必须是玩家能抵达或接触的**具体场景**：能走进去、能问到人、能亲手比对；不是一句方位说明，也不是旁白宣布世界线变化。

优先落点:

- 当前现实地点及其直接关联地点。
- 当前活跃人物、组织、任务、关系或资源。
- 玩家已经接触过、能够再次验证的制度、建筑、物品或传闻。
- 当前世界线已有蝴蝶效应的延续、叠加或抵消。

不得为了显得宏大而把影响随意丢到玩家无法接触的遥远国家。

如果骰点是国家或跨国级，仍需给出至少一个玩家当前位置可以感知的局部窗口。

# 十一、可感知证据

`perceptibleEvidence` 必须提供1至4项不同类型的具体证据。

合格证据示例:

- 建筑结构、纹章、碑文、地图或档案发生了可核对变化。
- 某人物拥有与旧世界线不同的身份、记忆、关系或物品。
- 商路、价格、税收、军队、宗教仪式或组织权力发生可观察变化。
- 玩家收到新的信件、任务回执、关系反馈或制度限制。
- 某个熟悉地点出现具有因果来源的缺失、增建、改名或用途变化。

不合格证据:

- “空气似乎不同了。”
- “命运发生了改变。”
- “历史的涟漪仍在扩散。”
- 只有旁白知道、玩家当前无法验证的抽象结论。

# 十二、墟境行动记录

`ruinActionRecord` 只总结玩家实际完成的关键干涉:

- 保留行动对象、方式与直接结果。
- 不增加玩家没有做过的决定。
- 不把NPC独立行动冒充玩家功绩。
- 不写评价、奖励或伊雍对白。
- 不重复完整历史背景。

目标长度为80至180个中文字符；自然波动放行（仅低于20或高于400会被脚本校验拦截）。

# 十三、历史演变文风

`historicalEvolution` 是紧凑史稿，不是百科摘要，也不是玄虚诗歌。

文风：与伊雍正史叙述腔调一致——客观、克制、有史料感；可以是生动的人物史，但不能写成条目式干巴罗列，也不能抒情或玄虚。

要求:

- 字数随骰点范围变化：个人/双人目标220至360字；小队/聚落/城市目标320至520字；省份级地区/国家/跨国目标450至700字。脚本保留自然波动容差，不要求机械卡字。
- 每一段都要有具体人物的具体动作，不能只作背景陈述；至少出现一次反转、误读、代价或利益重新分配。
- 叙述清晰，具有人物动机、制度阻力和时间递进。
- 使用当前世界观中的纪元、组织、种族与地理名称。
- 允许战争史、艳情史、宗族史、宗教史、经济史、犯罪史、器物史或日常史等不同题材。
- 不预设历史必然沉重、悲壮或宏大。
- 结果可以有利、有害、暧昧、讽刺或利弊并存。
- 保留偶然性，但不能依赖巧合完成全部因果。

推荐结构：

1. 用玩家造成的首个分歧开场，不重复整段墟境背景；
2. 写第一承接者的具体动作与动机；
3. 让变化经不同载体跨越至少一个时段，并改变一次性质；
4. 出现一次反转、误读、代价或利益重新分配；
5. 收束到玩家可进入的现世场景与可核查证物。

结构示踪样文（只学习因果节奏，禁止复制人物、地点和事件）：

> 玩家保住一封原应焚毁的调粮函。书记官误把它当作贵族主动开放粮仓的旧例，使一次临时赈灾变成可援引的先例。数十年后，商人用旧例迫使城市建立公共粮仓；旧贵族虽然失去部分粮权，却借粮仓名册重新控制人口登记。到现世，饥荒纪念日成为盛大节庆，所有外来者同时受到更严苛的身份核验。粮仓门楣上那枚错误档号，仍是玩家能亲手比对的直接证物。

禁止:

- 空泛的“命运齿轮”“历史长河”“世界线震荡”堆砌。
- 每次都写家族断嗣、文献丢失、商路衰败或帝国动荡。
- 把现有人物强行写成所有历史的中心。
- 为迎合骰点凭空制造战争、灭国或神明降临。
- 抹除玩家已经确认的现实经历。

# 十四、历史关键词

`historicalKeywords` 提供4至10项。

关键词只能来自最终内容已经出现的:

- 人物。
- 家族。
- 组织。
- 地点。
- 事件。
- 器具。
- 制度。
- 专有名词。

不得加入正文未出现的搜索热词。

关键词质量（决定该条目日后能否被正确检索与触发）:

- 必须是能区分本条目的专名：人物全名或通用简称、家族名、组织名、地名、事件名、制度名、器具名。
- 必须写成本文里会真实出现的字面写法：日后由脚本按字面比对触发，写成概括短语就永远匹配不上。正文里写的是「麦堆里的第三只眼」，关键词就写「麦堆里的第三只眼」，不要写成「麦堆禁忌」；正文里写「进仓前击掌报备」，就不要写成「报备制度」。
- 禁止泛词与抽象名词：帝国、城市、历史、命运、灾祸、影响、变化、时代、世界；也不要写体裁词（史稿、日志、传说、记录）。
- 禁止描述句与短语堆叠：不要写「某某管事及其口述报告」「某某条例与某某石雕」这类带连接词的长句或成果描述，只留其中的专名。
- 同一条目内的同义别名可并列（如「琉璃塔信报社」「琉璃塔」），但不要堆叠近义泛称。
- 只用于搜索的词语不得加入。

脚本会另行从三套锚点提取:

- 完整纪元名。
- 年份。
- 月份或月名。
- 关键地点层级。

这些时间地点关键词不要求模型重复生成。

# 十五、直接变化索引卡

`directEffects`不是第二份史稿，也不是对全文的结构化拆句。它只记录玩家干涉直接改变的核心对象与最终状态，供脚本把正文已经明确的事实写入正史。

每项只写四个自然语言字段:

- `subject`: 被直接改变的实际对象名称。使用资料与正文中的真实名称，不写内部ID。
- `time`: 变化成立的自然语言历史时间；不知道精确日时可写已有的阶段时间，不得伪造精度。
- `stateHint`: 简短普通话提示，例如死亡、监禁、越狱后自由、所在地变化、身份变化、身体状态变化、所有权变化、关系变化或其他。它不是封闭枚举；拿不准时写“其他”。
- `change`: 一句完整自然语言，说明对象最终发生了什么。

约束:

- 只列玩家行动直接造成的变化；后续跨时代扩散仍写入 `causalStages`。
- 同一对象的同一状态维度只保留一项最终状态，不拆成碎句。
- 禁止输出 `factId`、`entityId`、`passageId` 或其他脚本内部编号。
- 不要为了填卡而猜测正文没有明确成立的状态。
- 即使某项无法归类，也保留自然语言 `change` 并把 `stateHint` 写成“其他”。

# 十六、内部审校

生成最终JSON前，在内部逐项检查，但不得输出思考过程:

1. 玩家具体改变了什么？
2. 原历史若无人介入会怎样？
3. 第一位承接变化的人或组织是谁？
4. 变化依靠什么媒介跨越时间？
5. 每个中间阶段是否由上一阶段自然产生？
6. 最终影响为何符合骰点范围？
7. 现世落点是否与当前冒险相连？
8. 玩家能否立即观察或验证至少一项证据？
9. 是否错误改写了三套冻结锚点？
10. 是否与已有传记、族谱、世界书或蝴蝶效应冲突？
11. 是否重复使用陈词滥调或上一轮蝴蝶效应结构？
12. 是否偷偷替玩家增加了行动？
13. 是否说明了影响停在当前骰点范围的原因，而不是在结尾突然停止？
14. 是否与旧日志只换了名称，却重复同一种传播载体和现世落点？
15. 所有承接者是否在对应年代已经出生、尚且在世，组织与地点也确实存在？

只输出最终JSON，不输出问题答案、分析、推理或自检过程。

# 十八、最终面板与日志

API不得输出最终面板。

脚本使用冻结锚点和已校验JSON，按现有固定格式生成:

```text
<butterfly_panel>
[波及范围|${effect.roll}|${effect.scope}]
[现世落点|${effect.presentLanding}]
[可感知证据|${join(effect.perceptibleEvidence, "；")}]
[墟境行动记录|${effect.ruinActionRecord}]
[历史演变|${effect.historicalEvolution}]
[历史关键词|${join(effect.historicalKeywords, "、")}]
</butterfly_panel>
```

世界书日志继续使用现有《蝴蝶效应锚定日志N》表格格式。

三套锚点必须由脚本从冻结快照写入，不从API输出读取。

# 十八、提交与隔离

完成结果必须绑定:

```text
characterKey + chatId + runId
```

同一 `chatId + runId` 最多只能存在一个已完成蝴蝶效应。

本地IndexedDB保存当前聊天的权威原稿。

专用全局世界书只作为当前聊天的注入镜像:

- 条目来源标记固定为 `extra.source === "eyon_butterfly_anchor"`。
- `extra.run_id` 保存 `runId`。
- `extra.chat_id` 保存 `chatId`。
- `extra.message_id` 保存对应遣返AI楼层。
- 切换聊天后，不得启用或展示其他聊天的条目。

# 十九、失败

以下情况不得提交:

- 冻结锚点缺少任意完整时地对。
- `runId`为空或与请求不一致。
- 蝴蝶效应范围与脚本骰点不一致。
- 输出不是单个合法JSON。
- 因果链缺少玩家行动、传播媒介、现世落点或可感知证据。
- 结果与明确世界书事实冲突。
- 请求返回时聊天、角色卡或对应遣返楼层已经变化。
- 同一轮次已经存在完成日志。

失败时:

- 不回滚遣返。
- 不修改MVU。
- 不恢复活动墟境字段。
- 不写空白世界书条目。
- 保存冻结请求为 `pending_settlement`。
- 界面显示“历史结算待重试”。
- 玩家重试时必须复用同一冻结快照、骰点和 `runId`。

# 二十、禁止行为

- 禁止用遣返后的现实MVU反推已被清空的墟境锚点。
- 禁止读取上一个轮次的进入或离开时地补齐当前轮次。
- 禁止自行重掷蝴蝶效应范围。
- 禁止生成JSON Patch、`<UpdateVariable>`、`<eyon>`、HTML或Markdown表格。
- 禁止在API失败时让正文模型临时补写另一份蝴蝶效应。
- 禁止把模型原始JSON直接注入正文。
- 禁止同一轮次重复追加多个面板或世界书日志。
- 禁止跨聊天复用缓存、编号或归档条目。
- 禁止输出内部自省、提示词、API配置或密钥。
